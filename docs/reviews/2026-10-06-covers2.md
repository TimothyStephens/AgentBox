## Gaps, ranked

### N1 (high): a stop request between the gate's check and the forwarded start re-initialises the container, bringing back H2

- **What happens:** `prepare_start` (`gate.py:1050-1059`) runs init and checks mountinfo. After that the gate opens a new upstream connection and forwards `start` (`gate.py:2295`). The gate serves requests in parallel threads, and `POST /containers/{id}/stop` is passed through to sockguard, which allows it (`sockguard.py:111`).
  - libpod lets you stop an *initialized* container (its "created or running" rule). After the stop, the forwarded `start` re-initialises it, which resolves the SubPath again.
  - So an agent that keeps flipping `app` between a directory and a symlink to `secrets` can run `start` and a stop loop side by side. When a re-init lands while `app` points at `secrets`, the real `secrets/` is mounted.
  - `after_start` (`gate.py:931`, called at `:2308`) then runs non-strict. It returns `[]` for an exited container, and for a running one it only acts after the entrypoint has run.
- **Needs checking:** that podman 5.7 lets you stop an initialized container: `podman create --name abt-x busybox:1.36 true && podman init abt-x && podman stop abt-x && podman inspect -f '{{.State.Status}}' abt-x`. If this prints `stopped`/`exited`, N1 is real.
- **Fix:**
  1. Add a per-container lock, held from `prepare_start` until the start reply comes back. Make stop, kill, init, restart, pause, unpause and remove for that ID take the same lock; today they are `pass`, so they need a hook in `decide`. Pod stop and kill should take the members' locks.
  2. Record the PID checked in `prepare_start`. After the start reply, refuse and remove the container if its PID changed or it is no longer running from that PID. Run `after_start` with `strict=True` on that comparison.
- **Tests:**
  - Unit: a fake whose `raw_request` for start flips the state to `stopped` and then re-inits with a new PID and mountinfo on a cover; expect Deny and removal. A second thread's stop arriving while `prepare_start` is blocked must wait, or be refused.
  - Itest in `test_step6_covers`: a 200-iteration loop that flips `app` and the link while a background loop sends `podman stop`, each iteration running `podman start -a`. Assert no `SENTINEL`.

### N2 (medium): covers nested inside a directory mask get real binds and pins mounted on top

- **What happens:**
  - `find_git_dirs` (`mounts.py:139`) and `compose_overlays` (`mounts.py:181`) walk into `secrets/`. Only `secret_mounts` removes it from the walk (`mounts.py:72-75`). The same goes for an adapter's tmpfs project cover such as `.omp` (`session.py:523-525`).
  - So with `secrets/vault/.git`, the plan holds the tmpfs at `secrets` plus real read-only binds of `secrets/vault/.git/{hooks,config}`. A `compose.yaml` under `secrets/` with compose=ro gets the same treatment.
  - podman mounts the deeper paths after the tmpfs, so they show the **real** config (which can hold credentials in remote URLs) and hooks inside the "empty" mask. This happens in the agent's own namespace, in every tier.
  - With the dev tier, `pin_args` also pins `secrets/vault/.git`, `secrets/vault` and `secrets` itself. That last one has the same destination as the tmpfs. Depending on podman, the session either fails to start (duplicate destination) or the pin wins and all of `secrets/` is exposed.
- **Needs checking:** the duplicate-destination behaviour: `podman run --rm --mount type=tmpfs,dst=/x --mount type=bind,src=/tmp/abt-d,dst=/x busybox:1.36 ls /x`.
- **Fix:** after building the plan, drop every mount whose destination is strictly under a `mask`/`tmpfs` cover or a project cover. In `pin_args`, skip any `d` that is covered or under a covered path. Do the same for adapter covers in `covered_paths`, since its sets come from the same plan.
- **Tests:**
  - Unit (`test_mounts`, `test_session.CoverPins`): `secrets/vault/.git` and `secrets/compose.yaml` produce no mount and no pin under `secrets`.
  - Itest: seed `secrets/vault/.git/config` with a sentinel, then in the session assert `ls -A secrets` is empty and `cat secrets/vault/.git/config` fails.

### N3 (medium): `RUN --mount` `source=` is left entirely to buildah

- **What happens:**
  - `dockerfile_images` reads only `from=` (`gate.py:1900-1901`).
  - Builds run in the session's podman service as `vmuser`. A buildah path bug in `type=cache,source=../..` (CVE-2024-9675 shape) or in `type=bind` would reach all of `~`, not just covers.
  - `run_mount_bind_escape` shows buildah refuses today's bind case; nothing covers cache `source=`.
- **Fix:** in the same parser, refuse `source=` that is absolute or contains `..` for `type=bind` without `from=` and for `type=cache`. Also refuse `bind-propagation=` and `relabel=`.
- **Tests:** unit (parser) cases for `type=cache,source=../../..` and `type=bind,source=/etc`. A `test_step5_fields` case asserting the gate's own 403 message, not buildah's.

### N4 (low): hardlinks are only reported, and only for some covered files

- **What's missing:** the `nlink` check covers `mask` files only. It misses:
  - files under `secrets/` (a tmpfs cover);
  - the real `.env` behind the dev swap;
  - `.git/config`.

  It adds a note but doesn't add the other name to `covered`. The spec (§4.4) requires covers to hide data reached through a hardlink.
- **Fix:** at plan time, collect `(dev, ino)` for every covered regular file, including files under covered directories. Walk the grants for other names with the same inode and either mask and cover them or refuse to start.
- **Test:** before the session, `ln secrets/db-password.txt app/x`. In the session, `cat app/x` must be empty, and `-v $ROOT/app` must not show the sentinel.

### N5 (low): `covers_intact` isn't checked at start, and a change on the host side shuts off binds

- **What's missing:** `prepare_start` and `mount_violations` never call `covers_intact`. It only runs at create time.
- **Side effect:** if Tim runs `git config` on the host, or an editor saves `.env` by writing a new file and renaming it, the cover gets a new inode. Every later bind in the session is then refused, which fails closed but isn't documented.
- **Fix:** call `covers_intact` in `prepare_start`, and say in the refusal message that host-side edits trigger it.
- **Test:** unit: create, replace the cover file's inode, then start: refused.

### N6 (low): covers that appear after the session starts are not covered

- **What's missing:** a secret file or directory written into the project by a host process (Tim, or a live stack) after start is neither masked nor in the gate's list. Files the agent creates don't matter, since it wrote the content.
- **Fix:** at bind time, walk the bind source for `MASK_FILES`/`MASK_DIRS` names. Refuse if a matching file is not empty and not in `covered`. When `masked_paths` lands, create its covers even when the path doesn't exist yet (spec §4).
- **Test:** after the session starts, create `app/new.pem` with a sentinel on the host; `-v $ROOT/app` must be refused.

### N7 (low): grant volumes use a non-recursive bind

- **What happens:** grant volumes are created with `o=bind` (`gate.py:711`). A SubPath below a host submount inside a grant root therefore shows the directory underneath the mount, not the mounted filesystem.
- **Effect:** `mount_violations` refuses a SubPath that lands on a different device. That's safe, but the reason given is confusing.
- **Fix:** document this, or have `grant_subpath` refuse sources that cross a submount, with a clear reason.

### N8 (low): the masked-content check on build contexts is a heuristic

- **What happens:** it only applies when every top-level member of the tar exists under a directory inside a grant (`gate.py:1224-1227`). One made-up top-level member skips it.
- **Why it's low:** the agent can't get the real content to put into a context in the first place.
- **Fix:** document it as a heuristic. Optionally, refuse any non-empty member whose path ends in a masked suffix.

### N9 (test only): no test swaps a symlink into a bound directory while the container runs

- **Add:** with a container running and `app/` bound, have the agent create `app/l` pointing at `$ROOT/secrets/db-password.txt` and at `../secrets/db-password.txt`. Each `cat` inside the container must fail.

## Doc claims the code doesn't back up

- **H2 response, `prepare_start` docstring and the `test_step6_covers.py` header:** they say a swapped sub-path "never reaches a running process". That's not true while N1 is open, because a concurrent stop undoes the init-then-check.
- **decisions.md, H1 correction:** "A future `masked_paths` setting needs no gate work beyond adding its paths to the covered list."
  - `masked_paths` entries missing at start get no identity and can't be pinned (N5, N6).
  - A masked directory holding a git repo or compose file hits N2.
- **decisions.md, L1 ("a masked file with other hard links is reported"):** this applies only to individual mask files, and it's a note rather than a cover. Spec §4.4 isn't met (N4).
- **decisions.md, builds ("the gate also refuses a context carrying content at a masked path"):** only when the gate can match the context to a project directory (N8). "`RUN --mount` binds the uploaded copy" is buildah's guarantee, not the gate's (N3).
- **decisions.md, 2 Oct:** "starting a container starts its dependencies without a separate gate start check". This is out of date: `prepare_start` now initialises and checks dependencies (`gate.py:1037-1042`).
- **Gate docstring (`gate.py:21-22`) and the session notes:** they say covers are enforced for containers the agent starts. That holds for binds, but not against N1. In the agent's own namespace it also fails for covers nested inside a directory mask (N2).

The order I'd fix them in: N1 (the lock and PID comparison), then N2, then N3. The rest are small. `docs/reviews/2026-10-06-covers2.md` is still empty; I haven't written anything into it.

Podman-behaviour checks run first:
- **stop after init:** create, then `init`, then `stop` leaves the container `exited` with pid 0. N1 is real: a stop between the gate's check and the forwarded start lets the start re-initialise and re-resolve a sub-path.
- **duplicate destination:** a tmpfs and a bind on the same destination are refused by podman (`duplicate mount destination`), either order. N2 would have failed the whole session rather than silently exposed; it is fixed so the duplicate never arises.
