# A4 audit: when the gate treats an object as the session's, and whether actions can reach it too early or reach objects the session doesn't own

I only read code and docs. I edited nothing, started no containers and ran no tests. "Read" in the table means I checked it in the code; "Unverified" means it depends on how sockguard 2.2.1 or podman behaves, which I couldn't check without running them.

**How ownership is recorded today.** For containers, pods, volumes, networks and built images, ownership is just the labels the gate stamps on them (`agentbox.dev-owner=<session>` and `agentbox.role=dev`, `gate.py:279-284`). The gate never keeps its own list of objects it has checked. Exec sessions are the exception: their IDs go into an in-memory set, `exec_ids`, which is only filled once the exec create has been forwarded (`gate.py:787-790`). Locally available images are never recorded as owned. The dev sockguard allows unowned images (`sockguard.py:146`).

## Gaps

### High

**G1. Actions can reach a new container or pod before its post-create check finishes.** Locations: `gate.py:763-777` (create → verify) and `gate.py:580-586` / `271-276` (`require_dev` trusts labels).
- **What it allows:** podman stores the container already carrying the stamped dev labels. During the inspect and verify window (slow on this host), a second connection can start, init, attach to or exec into it by name, or by an ID read from the list call. So something only the post-create check would catch can run before it is removed.
- **Fix:** have the gate keep its own record of checked objects. Keep a `verified` set of IDs (containers, pods and pod infra IDs), added to only after `verify_created` passes. `require_dev` (including exec create) should resolve the ref to an ID and require it to be in the set as well as carry the labels. The simplest variant is a gate-wide lock: create plus verify holds it exclusively, every other request holds it shared.
- **Test:** a unit test with a fake gate whose `container_violations` blocks on an Event. Send a start for the same name on another thread and assert 403 and that nothing was forwarded upstream. Add an integration case that creates and immediately starts in a loop, and asserts no start succeeds before the create returns.

**G2. The post-create check fails open when the response can't be parsed.** Location: `gate.py:251-256`.
- **What it allows:** any response the parser can't read is treated as "create failed, nothing to check", but a container may exist. Client request headers are forwarded unchanged, so the client can shape the upstream response. One example: an interim `1xx` status line before the final `201` would make the split land on the wrong part. I haven't confirmed sockguard does this, so this is unverified.
- **Fix:**
  - Read the response with `http.client.HTTPResponse` (it skips `1xx`).
  - Remove `Expect` and other unneeded request headers on creates.
  - Fail closed: if the final status is 2xx and no ID can be read, look the object up by the requested name, remove it and refuse.
- **Test:** a unit test with a fake upstream socket returning an interim `1xx` response, then a `201` whose stored document has a violation. Expect the DELETE call and a 403. Add a second case with a 2xx and an unparseable body.

**G4. Named volumes this session doesn't own can be mounted (unverified).** Locations: `gate.py:361`, `405-407` (binds only) and `221-223` (post-check covers binds only).
- **What it allows:** a create that mounts an existing named volume (libpod `volumes`, compat `Binds` without a leading `/`, `Mounts` of type volume) or uses `volumes_from` / `VolumesFrom` is not checked by the gate. Whether sockguard's owner isolation covers volume references inside create bodies isn't established by any test. If it doesn't, the dev stack can read or write other stacks' volumes. The design says live-stack volumes are never granted.
- **Fix:**
  - Before forwarding, refuse `volumes_from` / `VolumesFrom`.
  - Run `require_dev("volumes", name)` on every named volume source (libpod `volumes`, `image_volumes` is fine, compat `Binds` and `Mounts` of type volume).
  - After create, require every `Mounts[].Type == "volume"` to name a volume with this session's labels, and reject any mount types other than bind, volume and tmpfs.
- **Test:** unit tests for each spelling. Add an integration case mounting a canary volume labelled for another project; expect 403 and nothing created.

**G8. A build can move an existing image tag the session doesn't own.** Location: `gate.py:489-527` (`t` is never inspected).
- **What it allows:** a session build tagged with the name of an existing image moves that tag to the session's image. Examples are the agent images (`localhost/agentbox-*`, used by other projects' sessions) or a live stack's image. That stack then runs the agent's image the next time it starts, outside the sandbox.
- **Fix:** for each `t`, normalise the name. If an image with that name exists, require labels `agentbox.project=<project>` and `agentbox.role=dev`. Otherwise refuse. Ideally also require a `localhost/` name, with a fixed refusal list for `agentbox-*`.
- **Test:** a unit test where a fake `image exists` reports an unlabelled `localhost/agentbox-omp`, and a `t` of that name is refused. Add an integration case with a pre-made unlabelled `abt-` image: build with its tag, expect 403 and the same image ID afterwards.

### Medium

**G3. A container that fails its check can be left behind, still usable.** Location: `gate.py:261,267`.
- **What it allows:** if the inspect or DELETE times out, or the DELETE doesn't return 2xx, the client gets a refusal but the labelled container remains and can be started later.
- **Fix:** with G1's verified set this is closed automatically, because the object is never added. Also retry the removal, check its status and log the outcome.
- **Test:** a unit test where `raw_request` returns 500 (or raises a timeout); assert that a later start of that name is refused.

**G5. Endpoints the gate leaves entirely to sockguard have no refusal test.** Locations: `gate.py:580-586` and `sockguard.py:101-122`.
- **What it allows:** query-named or body-named targets (commit, kube, network connect, image tag, rm, load) are refused only by sockguard's rules. Loosening those rules would silently expose them.
- **Fix:** refuse these paths in the gate too (explicit deny list).
- **Test:** a unit table of these paths expecting `Deny`. Add a short integration check that they return 403 through the real stack.

**G6. Paths aren't normalised.** Location: `gate.py:554-586`.
- **What it allows:** `RESOURCE` checks only the first segment after the kind. A path with dot segments, a doubled slash or an encoded `/` can resolve differently downstream than the gate assumed. This is unverified: podman and Go routers may clean or redirect such paths.
- **Fix:** refuse any target whose decoded path contains `..`, `//`, `%2F` or `%5C`, or that differs from its normalised form.
- **Test:** unit tests for each form, expecting `Deny`.

### Low

- **G7.** `exec_ids` aren't tied to a container and are never pruned. Store `exec_id → container ID` and re-check that the container is owned on start.
- **Pulls** can move a shared tag to its upstream version. Consider refusing pulls of tags already used by containers the session doesn't own.
- **Images:** any local image can be inspected, including its history, and used as a `FROM` or run image. Images belonging to other stacks may expose their ENV or build arguments. Decide whether to scope image reads by label.

## Checked and sound

- Every request on a single named container, pod, volume or network goes through `require_dev`, which requires both labels (unit test plus itest CANARY_* and SELF_*).
- The session's own agent, proxy, sockguards and holder have role ≠ dev, so they are out of reach. The internal network's role `network` keeps it out of reach too.
- Exec start, resize and remove are allowed only for exec sessions the gate created, and the record is filled only after a successful create. A gate restart fails closed.
- Joining a pod requires the pod to be owned. The post-create check re-checks the pod's labels and its infra ID for `container:` modes.
- Owner labels can't be changed after creation through any endpoint sockguard allows.
- Teardown selects by `agentbox.session`, which the gate stamps on everything it creates.

## Doc claims the code doesn't back up

- **gate.py docstring and decisions.md** ("after every create … removes it and refuses"): the removal happens only after the check, and actions in the meantime aren't blocked (G1). The check is also skipped when the response can't be parsed (G2).
- **design.md, "Never granted: … volume deletion":** `DEV_RULES` allows `DELETE /volumes/*` and `allow_remove_volumes`. This is reasonable for the dev stack, but the doc should say "on the live stack".
- **design.md, "Uploads land in the live stack's own volume, which no agent session is ever granted":** nothing in the gate enforces this (G4).
- **design.md exec bullet** ("requires the project's compose label or the session's owner label"): the code requires only the owner label plus role dev. That is stricter, so update the doc.
- **design.md, "image pulls … pulls a create triggers":** the gate has no create-triggered pull path. It works only because creates don't pull.

## Builder's response (1 Oct)

### The timing question: can an object be used before the post-create check finishes?

**Before this fix: yes.** Podman stores a new container or pod with the dev labels already on it, and `require_dev` trusted those labels. So from the moment podman answered the create until `verify_created` had inspected it (and, on a violation, removed it), another connection could start, init, attach to or exec into it by name or by an ID from a list call. The unit test `test_g1_start_during_the_check_is_refused` reproduced this: with the check held open on an Event, a start of the same name passed the gate (it failed before the fix).

**Now: no.** The gate keeps its own record, `verified`, of the IDs whose post-create check passed. Covered kinds:
- containers;
- pods and their infra containers;
- volumes, by name;
- networks, by ID and name.

An ID is added only at the end of a passing `verify_created`. Every request that names a container, pod, volume or network now needs two things: the dev labels, and the object's resolved ID in `verified`. That covers start, init, attach, exec create, logs, stop and delete. Exec sessions are tied to the container they were created on, and need that container to be verified when they are used.

So during the check window the object exists, but nothing the agent sends can reach it. If the check fails, the ID never enters the record. That holds even when the removal itself fails: the delete is retried and logged, and the ID goes on a `refused` list. A gate restart starts with an empty record and fails closed.

Pod start goes further: it requires every member container to be in the record and re-checks each one. This closes the case where a pod is started while a member's check is still running.

Tests:
- `test_g1_a_container_not_yet_verified_cannot_be_used` covers start, exec, attach and init;
- `test_g1_start_during_the_check_is_refused` covers the concurrent start;
- `Starts.test_pod_start_needs_every_member_checked` covers pod start;
- `test_g3_inspect_failure_removes_and_never_verifies` covers a failed check.

No integration loop was added. The race is closed by construction, and the unit test drives the real `verify_created` concurrently. An integration loop could only show the race happening, not prove it can't.
