## Gaps, ranked

### High

**H1. A container in an infra pod can bypass network pinning.** gate.py:348-349, 422-424, 426-444, 217.
- **What it allows:** if the agent creates a pod that has an infra container but doesn't share the network namespace, or sets its own `netns` on a container joining an infra pod, the container can end up on podman's rootless default (pasta), which reaches the LAN. Neither the check before forwarding nor the one after it catches this.
- **Why it slips through:**
  - `pod_has_infra` only looks at `InfraContainerID`.
  - `rewrite_pod` never checks or overwrites the pod's shared-namespace list. `LIBPOD_FIELDS` lists `share`, but podman's JSON name is likely `shared_namespaces` (verify).
  - In the pod branch, the client's `netns` is left as sent.
  - After create, a container in a pod skips the networks check, and `pasta`/`slirp4netns` aren't on the `NetworkMode` denylist.
- **Verify:** whether podman accepts each variant. The gate doesn't stop either of them.
- **Fix:**
  1. In `rewrite_pod`, refuse or overwrite the shared-namespace field so that `net` is always included.
  2. In `pod_has_infra`, require the pod's `SharedNamespaces` to contain `net`. Otherwise drop the membership and pin the container, the same way infra-less pods are handled.
  3. In the pod branch, delete any client `netns`, `Networks` and `network_options`.
  4. After create, when the container is in a pod, require `NetworkMode == "container:<infra id>"` exactly, and check the infra container's own networks == {session net}.
- **Tests:**
  - Unit: a pod create with a share list that leaves out `net` is refused or rewritten.
  - Unit: a container in an infra pod has its `netns` stripped.
  - Unit: `container_violations` flags `NetworkMode` values `pasta`, `slirp4netns` and `bridge` when the container is in a pod.
  - Itest (`test_c`): a raw-API infra pod without net sharing, plus a member container, is refused, or ends up on the session network only.

### Medium

**M1. The pod check after create accepts an infra container with no network.** gate.py:245.
- **What it allows:** `set(Networks) - {session net}` is empty when the infra container has no named network (pasta/slirp4netns), so that pod passes.
- **Fix:** require `set(Networks) == {self.network}` whenever `InfraContainerID` is set, require `SharedNamespaces` to contain `net`, and require the role label as well as the owner label.
- **Test:** unit tests for `pod_violations`, which currently has none: empty `Networks`, extra network, `HostNetwork`, port bindings, `net` not shared.

**M2. The check after create fails open.** gate.py:252-256, 263-267, 261.
- **What it allows:** a create that succeeded but whose reply the gate can't parse skips verification entirely. An inspect that times out or raises leaves the container in place (labelled, so it can be started later), and a failed delete still reports "removed it".
- **Fix:**
  - Use the HTTP status: a 2xx reply with no `Id` gets a deny, and the gate removes the container by the name it forwarded.
  - Wrap the inspect so that any exception means delete, then deny.
  - Check the delete's status, log failures loudly and mark the ID as refused (refuse `start` on it).
- **Tests:**
  - Unit: `verify_created` with a fake `raw_json` that raises calls the delete.
  - Unit: a 201 reply whose body can't be parsed is denied.
  - Unit: a failed delete is logged and the ID is blocked.

### Low

**L1. Network create doesn't normalise field names and doesn't check driver or options.** gate.py:91, 93-94, 446-455, 559.
- **What it allows:** an agent-made network can use any driver, options (including leaving out `isolate=strict`), bridge interface name or subnet, for example one overlapping 10.0.0.0/24. It's only harmless because nothing can attach to it today.
- **Note:** `NETWORK_FIELDS` is defined but never used.
- **Fix:**
  - Add `"network"` to `CANON`.
  - Refuse any driver other than `bridge`.
  - Refuse `network_interface`, client options other than `isolate`, and client subnets/IPAM.
  - Force `isolate=strict` and `ipv6_enabled=false`.
- **Test:** unit refusals for each field, and a case-variant `INTERNAL: false`.

**L2. Network connect/disconnect relies on sockguard alone.** gate.py:580-585; sockguard.py:111-119.
- **What it allows:** the gate checks the network but not the container named in the body, so blocking this depends entirely on `DEV_RULES` never listing `connect`.
- **Fix:** refuse `networks/*/connect|disconnect` explicitly in the gate, on both API surfaces.
- **Test:** a unit test for the gate denial, and an itest line in `test_c` (raw-API connect to the session network gets 403).

**L3. `network_options` passes through on containers and pods.** gate.py:327-382, 426-444.
- **What it allows:** client network options (including pasta arguments that forward ports) reach podman. They're ignored while the mode is `bridge`, but they would take effect the moment H1 or a future change lets a non-bridge mode through.
- **Fix:** pop `network_options` in both rewrites. Also strip compat `HostConfig.NetworkMode` options if podman parses any.
- **Test:** a unit test that the field is gone after each rewrite.

**L4. Path forms the regexes don't match skip the gate's rewrites (verify).** gate.py:42-52, 554, 580-586.
- **What it allows:** a trailing slash or other path form that podman's router still serves as a create would get only sockguard's checks, with no pinning or port refusal.
- **Fix:**
  - Normalise the path (collapse `//`, strip a trailing `/`) before matching.
  - Deny any POST whose last segment is `create` but that matched no rewrite.
- **Test:** unit `decide` calls for `/libpod/containers/create/` and `//libpod/containers/create` are rewritten or denied.

**L5. Test gaps where the code itself is sound.** Add unit tests for:
- `publish_image_ports`
- `PublishAllPorts`
- compat `NetworkMode: ns:…`
- libpod `netns` set to `pasta`/`slirp4netns`
- pod `netns` host/path refusals
- an itest that brings up a pod with an infra container (compose's default doesn't, so that path has never run against real podman)

## Checked and sound

- **Containers not in a pod (libpod):** the network mode, networks and CNI networks are overwritten whatever the client sends; only aliases survive.
- **Compat creates:** network mode and endpoints are overwritten; port bindings and publish-all are refused.
- **Case-variant field names:** strict parsing refuses keys that differ only in case, and creates are normalised to exact spellings before checking. Network create relies on strict parsing plus the gate's key coming last.
- **Ports on containers and infra pods:** refused before forwarding and checked again after create.
- **Infra-less pods (podman-compose's default):** membership is dropped and each container is pinned.
- **Named resources:** the session's own network can be read but not deleted, and other resources must carry the dev labels.
- **Operations the gate doesn't handle itself:** kube play, checkpoint restore with published ports, container update and network connect are denied by sockguard's deny-all (the gate passes them through).
- **The agent's own network:** it is never agent-controlled; the launcher creates it as internal with `isolate=strict`.

## Doc claims the code doesn't back up

- **gate.py:9 and :13, decisions.md:312** say pods get "the same network rules" and are "pinned the same way". That only holds if the pod shares its network, which isn't enforced (H1).
- **design.md:277** says any other network "is rejected". The code rewrites it rather than rejecting it, and the network name is `<session>-int`, not `<project>_app`. design.md:399 (the selftest table) still says `<project>_app` too.
- **design.md:643** marks pod joining "[x] (step 5)", but that's covered by unit tests with a faked infra check only. No real-podman test covers an infra pod.
- **The gate's docstring (line 14)** says networks are created "forced internal". That's true, but the driver, options and isolation aren't checked (L1), so "internal" is the only property it guarantees.
