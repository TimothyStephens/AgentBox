# Review of steps 3–4 (e35bc69..f242f10)

I read the four docs, CLAUDE.md, the steps 1–2 review, and every file changed since e35bc69. I ran nothing that starts containers and edited no files; `docs/reviews/2026-10-01-steps-3-4.md` is still empty. I couldn't read files outside the repo, so anything that depends on what sockguard, podman-compose, OMP or Claude Code do internally is marked **PLAUSIBLE** and needs a test. **CONFIRMED** means the code alone shows it.

The biggest problem: the observe tier probably leaks the live stack's secrets through two endpoints it allows. The tests only check that `Config.Env` comes back empty, so they can't catch it.

## Findings, most severe first

### 1. HIGH: the live stack's environment leaks through `top` and through `CreateCommand` in inspect (PLAUSIBLE, both)
**Where:** `agentbox/sockguard.py:42-44` (the `top` endpoints and libpod inspect are allowed with any query string) and `:71-74` (the only env redaction is `redact_container_env`).

- **Through `top`:** podman-top(1) says that when you pass ps(1) flags, podman falls back to running `ps` with those flags inside the container. So `GET /libpod/containers/<live>/top?ps_args=eww` (or the Docker `/containers/<live>/top?ps_args=eww`) would print every process's environment. It also starts a process in a live container, which observe is supposed to forbid.
- **Through `CreateCommand`:** libpod inspect includes `Config.CreateCommand`, the full podman command line that created the container. podman-compose passes `environment:` entries as `-e KEY=VALUE` on that command line. Sockguard is built around the Docker API, so it probably blanks `Config.Env` and leaves `CreateCommand` alone. The same applies to `Config.Cmd`/`Args`, `Config.Healthcheck` and `State.Health.Log`.
- **Exploit:** a `pods` project observing `media_server` reads gluetun's VPN credentials. Under the credential rule, those must never enter a sandbox.
- **Test coverage:** `runner.py:195` and `test_step4_sockguard.py:141` only check that `Config.Env` is empty. The fixture uses `env_file:`, which probably reaches podman as a file path rather than as `-e` values. Nothing searches the full inspect or `top` output for the live stack's own secret; `test_c` only checks for `secret-of-{OTHER}`.
- **Fix:**
  - Allow `top` only with no query string, or drop `top` altogether.
  - Drop libpod inspect and keep only the Docker `/containers/*/json`, or check that sockguard strips `CreateCommand`.
  - Test: give the live fixture an `environment: SECRET=secret-of-live` line, then search the raw output of both inspect endpoints, `top?ps_args=eww`, list and pod inspect for that value.

> **Response (builder, 1 Oct): CONFIRMED and worse than stated; fixed.** Reproduced by `test_step4_sockguard.test_h_live_stack_secrets_do_not_leak`: the live fixture now has an `environment:` secret besides its `.env` value, and libpod inspect returned **both** (through `CreateCommand`), as did `podman --remote inspect`. Docker-API inspect, both container lists and `top?ps_args=eww` did not leak (`top` answered 500 here because busybox's `ps` rejects the flags, but it still runs a process inside a live container). Fix: the observe tier allows container lists on both surfaces, inspect and per-container stats through the Docker API only, and logs only with `observe_logs`; libpod inspect, `top` (both surfaces) and pods are denied. The test now passes and covers every observe endpoint plus `podman --remote inspect`; the selftest checks libpod inspect, `top` and the pod list are refused and that Docker-API inspect has an empty environment. Cost: `podman inspect`, `podman top` and `podman pod ps` stop working under observe; the session notes say to inspect with `curl --unix-socket /run/agentbox/podman.sock http://d/containers/<name>/json`.

### 2. MEDIUM: a repo can turn approvals off in `lockdown`
**Claude (CONFIRMED in code):** `adapters/claude.py:51-54` always sets `hasTrustDialogAccepted` and `bypassPermissionsModeAccepted`, including when approvals are on.
- Because the folder counts as trusted, a repo's own `.claude/settings.json` takes effect with no prompt: its hooks (shell commands that run at session start or on tool use), its `permissions.allow` rules, and its `defaultMode`.
- **Exploit:** a malicious repo in a `lockdown` project runs code, and Claude edits files, with nothing asked.

**OMP (PLAUSIBLE):**
- OMP probably also reads config, extensions and `.mcp.json` from the project directory.
- `~/.omp/agent` is persistent and writable per project. Unless Tim creates his own `mcp.json`, nothing is mounted over `agent/.mcp.json`, and nothing ever covers `agent/extensions/`. One session can plant an extension or an MCP server command that every later session of the project runs.

**Test coverage:** `test_omp.py:305` and the Claude tests only check the command-line flag. Nothing checks that a lockdown session actually asks before acting, and `olock` only runs the selftest, never OMP itself.

**Fix:**
- When approvals are on, don't pre-accept trust or bypass mode.
- Seed `permissions.disableBypassPermissionsMode: "disable"`, or better, a managed settings file baked into the image.
- For OMP: mount empty read-only placeholders over `agent/extensions` and `agent/.mcp.json`, and find out which project-local config OMP loads.
- Add an itest: lockdown, the stub model asks for a bash tool call, and the command must not run.

> **Response (builder, 1 Oct): CONFIRMED for Claude, fixed; OMP's persistent agent dir fixed; OMP project-local code deferred to Tim.**
> - **Claude:** reproduced by `test_review_1001.test_claude_tool_call_runs_only_with_approvals_off`. A stub model returns a Bash tool call, and the repo carries a `.claude/settings.json` with an allow rule, `defaultMode: bypassPermissions` and a SessionStart hook. With the old pre-trust, the lockdown session ran the command (checked by putting the old behaviour back for one run). Fix: with approvals on, neither trust nor bypass mode is pre-accepted, and a read-only managed policy at `/etc/claude-code/managed-settings.json` sets `disableBypassPermissionsMode: disable`, `allowManagedHooksOnly` and `allowManagedPermissionRulesOnly` (names checked in the image's Claude Code build). The command and the hook no longer run, while a control project with approvals off still runs the command, so the stub works. Switching a project to lockdown revokes earlier trust (unit test).
> - **OMP:** `test_review_1001.test_omp_tool_call_runs_only_with_approvals_off` shows `--approval-mode=always-ask` holds in `-p` mode ("requires approval but no interactive UI available"), with a yolo control. The persistent agent dir's code-loading places (`extensions/`, `hooks/`, `tools/`, `.mcp.json`, `mcp.json`, `settings.json`; found in OMP's discovery source) are now covered read-only and empty, so one session cannot plant code for the next. Tim's own `mcp.json` still takes `.mcp.json`'s place when it exists.
> - **Deferred to Tim:** OMP also loads extensions, hooks, tools and MCP servers from the *repo* (`<project>/.omp/`, `.claude/`). OMP has no switch for project-local hooks or tools; `--no-extensions` would also drop the plugins installed in `~/.omp`. For `lockdown`, the choice is to accept that repo-provided OMP code runs without asking, or to run lockdown OMP sessions with `--no-extensions`, losing the plugins.

### 3. MEDIUM: the `~/.omp` whitelist accepts link targets anywhere inside `~/.omp` (CONFIRMED)
**Where:** `adapters/omp.py:68`. The only check is `_inside(real, omp_home)`.
- So `pylibs -> .` would mount the whole `~/.omp` read-only, including `agent/models.yml` with the real keys, `models.yml.backup`, `mags-codedev.yaml` and every project's sessions. `plugins -> agent` would do the same for the agent directory.
- **Exploit:** the links are written on the host, and `omp-workspace` is still in use with `~/.omp` mounted read-write into a privileged container. A compromised legacy session, or a repo opened in one, can repoint `pylibs` and thereby reach every agentbox OMP session.
- **Related gaps:**
  - Whole version directories are mounted without looking inside them (hard links, `.omp-env.json`).
  - `repos/*/.git/config` may hold remote URLs with tokens in them, which the credential rule forbids.
  - `unchanged()` (`omp.py:152`) re-checks only the three links, while `run_args` resolves the version directories again (`session.py:415`).
- **Test coverage:** `test_link_out_of_omp_refused` only covers a target outside `~/.omp`.
- **Fix:**
  - Require `realpath == ~/.omp/versions/<v>/<name>`, and require `<v>` to be a real, non-symlink entry of `versions/`.
  - Re-check the version directories in `unchanged()`.
  - Refuse a repo whose git config has credentials in a URL.
  - (Version names like `..` are already refused by the clean-destination check in `hardening.py:90`.)

> **Response (builder, 1 Oct): CONFIRMED, fixed.** Unit tests (`OmpMounts`) reproduced all four shapes (`pylibs -> .`, `plugins -> agent`, a target that is a version dir rather than `<v>/<name>`, a target in the wrong subdir); they were accepted before. Now:
> - each target must be exactly `~/.omp/versions/<v>/<name>`, and `<v>` a real directory there;
> - `unchanged()` re-checks the version directories;
> - the session is refused if a credential file in `~/.omp` (models.yml and its backup, mags-codedev.yaml, .mcp.json, mcp.json) has another hard link;
> - the session is refused if a mounted repo's git config has credentials in a remote URL (the credential rule).
>
> Plain `.omp-env.json` is a provenance marker (manifest hash and install time), not a secret.

### 4. MEDIUM-LOW: pod endpoints probably aren't scoped (PLAUSIBLE)
**Where:** `sockguard.py:45` allows `/libpod/pods/json` and `/libpod/pods/*/json`. Docker has no pods, so sockguard's label filter may not apply to them.
- **Exploit:** the agent lists every pod on the host (media_server, deploy) with member container names and IDs, the pod's create command and its port bindings.
- **Test coverage:** the test only checks `PODPS_RC=0`.
- **Fix:** drop both rules (the observe commands don't need pods), or add a canary pod to the selftest.

> **Response (builder, 1 Oct): CONFIRMED, fixed.** `test_h` showed `/libpod/pods/<another project's pod>/json` answered 200. Both pod rules are removed; observe does not need them. The test and the selftest check the pod endpoints are refused.

### 5. MEDIUM-LOW: keys may be written to persistent OMP logs (PLAUSIBLE)
**Where:** the real `~/.omp/logs/` contains `http-400-requests/*.json` and `native-panic-*.log`. In a session, `~/.omp/logs` is persistent per project.
- If OMP dumps request headers on an HTTP 400, or the environment on a panic, the key ends up at rest under `~/.local/share/agentbox/<project>/omp/logs`.
- **Test coverage:** the itest stub never returns an error, so this is the same blind spot as the previous review's #1, on the error path.
- **Fix:** make the stub answer 400 once, then search the state directory for the key.

> **Response (builder, 1 Oct): NOT REPRODUCED; rejected, test kept.** `test_step3_omp.test_key_not_at_rest_after_an_http_400`: the stub answers 400 to a marked prompt after OMP authenticated with the fake key. OMP writes `http-400-requests/<id>.json` into the kept per-project logs, but neither it nor anything else in the state, logs, backups or run dir contains the key. The test stays as a regression check.

### 6. LOW: the launcher's mount audit would allow mounting the raw podman socket
**Where:** `session.py:379` allows any mount source inside the session run directory, and that directory holds `podman/podman.sock` and `sockguard.yaml`.
- Today only sockguard mounts the socket. But a future adapter that mounts something from the run directory could hand the agent the unfiltered podman API, and the audit wouldn't stop it.
- **Fix:** keep the service socket outside the allowed sources, or have the audit refuse it explicitly. Add a selftest case that no unix socket other than `/run/agentbox/podman.sock` exists inside the sandbox.

> **Response (builder, 1 Oct): CONFIRMED as latent, fixed.** The podman service now lives in `<run>/services/<session>/`, outside the session run dir, so it is no longer an allowed mount source. The argv audit also refuses any socket as a bind source except sockguard's (`RawSocketNeverMounted`). The selftest case for "no other socket in the sandbox" was not added: OMP's own daemons create sockets in its `run` tmpfs, so a blanket check would be noise. The audit is the guard.

### 7. LOW: the observed stack defaults to the project's name
**Where:** `session.py:76`. An agentbox project named `deploy` or `media_server` with the `pods` preset silently gets observe access to that live stack.
- **Fix:** at session start, check that the stack's `com.docker.compose.project.working_dir` label is inside the project root; otherwise warn or refuse.

> **Response (builder, 1 Oct): CONFIRMED, fixed.** When `compose_project` is not set explicitly, the session refuses unless every container of that compose project was brought up from inside the project root (`com.docker.compose.project.working_dir`). An explicit `compose_project` is Tim's choice and is trusted (`LiveStackOwnership`).

### 8. LOW: the derived images
- **Unhashed pip installs:** `podman-compose` and `debugpy` are installed with pip without `--require-hashes`, and their dependencies (pyyaml, python-dotenv) are unpinned. Only podman-remote is checksum-verified.
- **Checksum without a signature:** that checksum comes from the same release page as the download, so nothing checks a signature.
- **Unusual org:** the URL's org is `podman-container-tools`; the checksum still guarantees what gets installed.
- **`/root` opened unchecked:** `/root` is opened to 0755 without checking what the base image keeps there (`.npmrc`, `.git-credentials`, `gh` config).
- **Old podman left in place:** Debian's podman 4.3 is still at `/usr/bin/podman`. With no-new-privileges and no capabilities this doesn't widen access.

**Fix:** pip `--require-hashes`, and a build step that lists `/root` and fails on credential-like files.

> **Response (builder, 1 Oct):**
> - **Unhashed pip installs: fixed.** `images/*/requirements.txt` pin the compose tool, python-dotenv and pyyaml (and debugpy for OMP) with sha256 hashes; the builds use `pip --require-hashes`.
> - **`/root` opened unchecked: fixed.** The OMP build now fails if `/root` holds credential-like files; it found nothing but an empty `.ssh` that an apt package creates.
> - **Checksum without a signature: accepted.** podman publishes a `shasums` file with each release and no signature on the static remote build; the pinned checksum fixes the bytes installed.
> - **The `podman-container-tools` org:** the podman project's own repository; GitHub redirects `containers/podman` there.
> - **Old podman 4.3 in `/usr/bin`: accepted**, as the review says; `/usr/local/bin/podman` comes first and the itest checks it.

### 9. LOW: an agent can write its own key into logs that are kept
Sockguard's access log records request paths and query strings, and squid logs CONNECT hostnames. Both are kept on disk. This is deliberate leakage by the agent of a key it already has, but it contradicts the "never in logs" wording.

> **Response (builder, 1 Oct): REJECTED under the credential rule.** Provider keys and the Claude token are accepted risk. An agent writing its own key into a request it makes is the same as sending the key anywhere, which nothing can prevent. The docs now say the "never in logs" checks cover accidental leaks.

The stale Containerfile comment is fixed.

## Checked and sound
- **Key handling:**
  - `ab keys set` uses a hidden prompt (never a command-line argument) and writes 0600 files atomically, with O_NOFOLLOW, in a 0700 directory.
  - `present()` refuses bad files instead of skipping them.
  - Keys are exported from read-only mounts just before the agent starts, and appear only by variable name in podman's config and in `models.yml`.
  - `models.yml` is written as JSON, so it can't be injected into.
  - The seed refuses `apiKey`, `!command` values and credential-looking headers.
  - The selftest scrubs key values from its output.
  - The step 3 itest really authenticates with the fake key before searching for it.
- **Audit mode** can't reach a real session: no setting selects it; only a test swaps it in.
- **`observe_logs = false`** removes the log rules on both API surfaces. No attach, events, archive or export path is allowed; only GET and HEAD are allowed, and deny-all is last.
- **Absolute links:** `/root/.omp` links and symlinks inside mounted directories resolve inside the session's own `~/.omp`. Version names like `..` are refused by the clean-destination check.
- **State-directory symlinks** are replaced or refused.
- **Sockguard container:** `--network=none`, no capabilities, read-only root, pinned digest whose signature Tim verified.
- **Podman service lifecycle:**
  - The service runs in a systemd-run scope inside the slice.
  - Stopping it checks the PID's command line first, so a reused PID is left alone.
  - gc scans `/proc` for orphaned services, and teardown runs on every signal.
- **Tiers:** the exec tier is refused, and dev is cut down to observe.
- **Binary pinning:** podman-remote is checksum-pinned with `ADD --checksum`.
- **Abstract sockets:** the host's abstract unix sockets can't be reached, because each session has its own network namespace.
