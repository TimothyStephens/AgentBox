# Audit of 785ee15: gate changes

I found one high-severity problem: the change to when the build record is written lets the agent add any image on the host to its project's record of its own builds. The rest are medium and low. Nothing was edited and no containers were started.

## Gaps, ranked

### High

**H1. Any image on the host can be added to the build record by echoing its ID.**

**Problem.** Before this commit, only the last stream line at `close()` counted. A successful build always ends with its real ID, and a failed build ends with an error line that clears the ID. Now `on_id` records *any* line that is exactly 64 hex characters, at the moment it appears (`builtrec.py:160-162`).

**How it is used.** A build containing `RUN echo <64-hex ID>` adds that image to `built-images/<project>.json`. A RUN step's stdout comes back as `{"stream": …}` lines; the exact framing is plausible from podman's build stream, not checked against podman here. The build can then fail and the entry still stays. `record_build` only asks whether the image exists.

**Impact.** It undoes the 1 Oct and 2 Oct image-allowlist decisions for that ID: the agent can run it, build `FROM` it, take its tag, and have pulls of it answered locally. The entry lasts across sessions until gc. A plausible way to learn the IDs: observe-tier inspect of live containers shows `"Image": "sha256:…"`, which covers a live stack's `localhost/` image.

**Fix.** Record only an ID that is the last stream line when the body ends, and write the record before the final bytes reach the client:
- In `pipe_back`, hold back any data that holds a candidate ID line until more stream data follows (then drop the candidate) or the body ends (size-0 chunk, or EOF).
- At the end, record, then flush.
- As a second check, `record_build` should also require the image's `agentbox.session` label to equal this session and its `Created` time to be after the build started. Labels alone are not trusted, but together with the end-of-body rule this narrows things further.

**Tests to add.**
- Unit (`BuiltRecord`): an ID line, then `STEP 2/2`, then the real ID → only the real ID is recorded. An ID line followed by `{"error":…}` → nothing recorded. A fake client socket shows the record is written before the last chunk is sent.
- Itest (`test_step5_gate`): a build with `RUN echo $(id of busybox:1.36, or of a throwaway abt- localhost image built outside the gate)`. Then `podman run` of that image through the gate must be refused, and the record must not contain it.

### Medium

**M1. Raw pod operations are forwarded by name, after a check done on the ID.**

**Problem.** `require_dev` resolves the pod name to an ID, but the request goes out with `target` unchanged, to the podman service, which has no sockguard behind it. If the name is freed and reused between the check and the forward (another session's pod, or a live stack's compose pod being recreated), DELETE, stop or kill acts on a pod that isn't the session's. The window is short and needs a second actor, but nothing else backs up this path.

**Fix.** In `decide`, rewrite the path segment to the returned ID for `pod_raw`, and for `pod_start` (forward the pod ID that `start_targets` resolved). Better still, build the forwarded path from the ID plus the allowed sub-path, rather than reusing the client's path.

**Test to add.** Unit: `decide(g,"DELETE","/v5/libpod/pods/p?force=true")` returns a target containing `pods/pid`. Same for `/stop`, `/kill`, `/start`.

**M2. The case-duplicate exemption is matched by bare key name.**

**Problem.** The exemption is right today: for every `DATA_MAPS` name in the bodies the gate allows, the value is a map whose keys are data, and nested values are checked again. But nothing pins that. Generic names like `config`, `options`, `volumes` and `networks` would also exempt any future object field with that name. This check is the guard against the PortMappings class of bug.

**Fix.** Key the exemption by body kind and path, e.g. `{("libpod","env"), ("libpod","Networks"), ("compat","HostConfig.PortBindings"), …}`, instead of by name.

**Tests to add.** Unit: case-duplicate *field names* under each data map are still refused, e.g. `Networks:{n:{aliases:[],Aliases:[]}}`, `volumes:[{Name:"a",name:"b",Dest:"/x"}]`, compat `HostConfig.PortBindings:{"80/tcp":[{HostPort:"1",hostport:"2"}]}`, `IPAM:{Config:[{Subnet,subnet}]}`.

### Low

**L1. Status codes show which objects exist.** A missing object gets 404, another project's object gets 403. This reveals container, volume and network names elsewhere on the host.
- **Fix:** answer 404 for "not this session's" too, which matches podman's "you can't see it". Keep 403 for objects that are the session's but not yet verified.
- **Test:** a request naming the selftest canary or another project's container gets 404 with the same body as an absent one.

**L2. Local pull answers show which images exist.** The pull path inspects before it checks the allowlist, and the messages differ.
- **Fix:** run `check_image` first, or give one message for both cases.
- **Tests:** unit tests for the `dev_images` branch and for a present but disallowed image.

**L3. The image-annotation allowance is implicit.**
- **Fix:** replace `ANNOTATION_HARD_REFUSED` with an explicit `ANNOTATION_FROM_IMAGE = ("org.opencontainers.",)`.
- **Tests:** an image annotation whose value differs from the container's; an image that was removed (refused); an image whose stopSignal differs from the config's.

**L4. envmerge is untested at the edges.**
- **Tests:** a `$` in a moved value is refused; three spellings of one name; a client-sent `envmerge` alongside a moved one.
- These only affect the session's own container's environment, so the risk is low.

**L5. Two smaller points.**
- `inspect` maps a podman 5xx to 404. Distinguish them and answer 502.
- `pod_raw` requests are only in the gate log. Note in decisions.md that the gate log is the audit trail for them.
