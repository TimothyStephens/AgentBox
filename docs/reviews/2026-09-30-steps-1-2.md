## Findings, ranked

### 1. HIGH — `make itest`'s token-leak checks are structurally blind; only Tim's manual `claude-live` actually exercises token persistence
**`tests/integration/harness.py:19,43-46`, `tests/integration/test_step1_core.py:42,92-96`, `agentbox/selftest/__init__.py:85-94`**

The automated suite writes a **fake** token (`fake-token-<run>-…`) and then greps state dirs, backups, logs, podman `inspect`, and selftest output for that string. But the fake token is never used to authenticate — Claude Code gets an env var that fails auth, so it has **no reason to write it to `~/.local/share/agentbox/<project>/claude/`** (`.credentials.json`, `.claude.json`, telemetry, crash dumps, etc.). The itest would pass whether or not Claude persists a *real* token. The design's central token claim ("never lands in session directories, logs, backups or selftest output", design.md:242, decisions.md:10) is only truly tested by `make claude-live` (`tests/live/claude_live.py`), which is manual and off by default.
- **Exploit:** Claude Code (or a future adapter) writes the real OAuth token into its persistent, non-tmpfs `CLAUDE_CONFIG_DIR` state, which survives `ab kill` (kept for `--resume`) and is copied into no backup but sits on disk indefinitely at a predictable path. CI stays green.
- **Covered?** No — the gap *is* in the coverage.
- **Fix:** In the live test, assert Claude actually authenticated (the `AB_OK`/tool run proves it) *and* that state files are token-free — which it does; the real fix is to make that check gate CI on a machine that has a disposable real token, or at minimum document that `make itest` proves nothing about token-at-rest and only `claude-live` does. Consider a stub that makes the fake token "authenticate" against a local responder so the persistence path runs under `make itest`.

> **Response (builder, 30 Sep): CONFIRMED, partly fixed.** Confirmed by reading the suite: the fake token never authenticated, so Claude's own post-auth writes were never exercised (no failing test was possible, since the gap was in what ran, not in what was checked). Fixed with `tests/integration/test_token_at_rest.py`: a stub Messages API on 127.0.0.1 inside the sandbox accepts the fake token; Claude sent it (`POST /v1/messages … TOKEN`), completed a turn (`STUB_OK`), wrote its transcript, `.claude.json` and a `.claude.json` backup, and none contain the token. The selftest now also checks podman's stored container config (it creates a container from the session's exact argv and inspects it). `make claude-live` (real token, real API) passed on 30 Sep with the same state-file check. Not done: running the real-token check in CI, as there is no CI and no disposable token; the design doc now says which test proves what.

### 2. MEDIUM — Masked secrets remain fully readable through `.git` history
**`agentbox/mounts.py:90-113,126-150` (git dir is bind-mounted; only `hooks`/`config` overlaid RO), design.md:236, decisions.md:45**

Masking (`/dev/null` over `.env`, tmpfs over `secrets/`) only touches working-tree paths. The entire `.git` directory is bind-mounted (read-write except `hooks`/`config`), and packed/loose objects are never masked. Any secret ever committed is readable with `git show <rev>:.env`, `git log -p`, or straight from `.git/objects`.
- **Exploit:** A repo that committed a real `.env`/`*.pem` once → agent reads it in any egress mode and, in `open`, exfiltrates it. This is the answer to your Q2 ".git history."
- **Covered?** No test; it's acknowledged in prose only.
- **Fix:** It genuinely can't be masked without breaking git. Strengthen the documentation into an operational gate (the design's own `ab` end-of-session secret scan, currently only an Open item) and surface committed-secret detection at `ab project add`/session start rather than burying it as a one-line residual.

> **Response (builder, 30 Sep): CONFIRMED, mitigated (cannot be fixed).** Reproduced by `F2CommittedSecretsWarned` (a `.env` committed then untracked: no warning before). Git history cannot be masked without breaking git, so the launcher now warns at session start, listing masked file names found anywhere in the history (`git log --all`, with `core.fsmonitor` off so no repo config runs on the host). Refusing such a project instead of warning is a policy choice left to Tim. The end-of-session scan remains an open item.

### 3. MEDIUM — `host_addresses()` fails open: the VM's own non-private addresses may not be blocked
**`agentbox/egress.py:45-65` and `squid_conf` 90-91,111-112**

`host_addresses()` catches `OSError`/`TimeoutExpired` (10 s each) and returns whatever it has, possibly empty. `squid_conf` only emits the `hostaddr` acl/deny **if `host_addrs` is truthy**. So if both `ip addr` and `getaddrinfo` fail or time out — plausible given CLAUDE.md's "host is slow at times, allow 60 s" warning against a 10 s timeout — the proxy is built with **no host-address deny rule**, and the config still succeeds silently.
- **Exploit:** The VM has a *public/non-RFC1918* address (or a global IPv6 — see #4). Under load the enumeration times out; that address is now reachable through the proxy in every mode, since only the static `private` list applies. (Today the LAN is `10.0.0.x`, which the `private` list still catches, which is why this is medium not high.)
- **Covered?** No — no test exercises the enumeration-failure path; unit tests always pass `host_addrs=["10.0.0.103"]` explicitly.
- **Fix:** Fail closed — if enumeration yields nothing, raise rather than emit a config with no `hostaddr` rule; and/or always include a configured static list of the VM's addresses.

> **Response (builder, 30 Sep): CONFIRMED, fixed.** Reproduced by `F3HostAddressesFailClosed` (enumeration failure produced a config with no `hostaddr` rule). Now a configured `host_addrs` list (default `10.0.0.103`) is always refused in addition to what is found, and with neither the session refuses to start; `squid_conf` itself refuses an empty list.

### 4. MEDIUM — Global IPv6 LAN addresses are not in the private list
**`agentbox/egress.py:17-19`**

`PRIVATE` covers IPv6 loopback/ULA/link-local/multicast (`::1`, `fc00::/7`, `fe80::/10`, `ff00::/8`) but **no global-unicast (`2000::/3`) equivalent of the LAN**. If the egress bridge is dual-stack and the LAN/host has GUAs, a public name resolving to the host's/another service's global IPv6 is only blocked by the `hostaddr` list (subject to #3) — the analogous IPv4 protection (`10.0.0.0/8`) has no v6 counterpart.
- **Exploit:** `open`-egress project reaches a LAN service by its global IPv6 literal or a name resolving to one.
- **Covered?** The selftest has IPv4-mapped and nip.io IPv4 cases; no global-IPv6 case.
- **Fix:** Decide the v6 posture explicitly — either disable IPv6 on the session/egress networks, or add the LAN's GUA prefix to the deny list and test it.

> **Response (builder, 30 Sep): CONFIRMED as an undecided posture; not exploitable on this host today; fixed by decision.** The host has no global IPv6 and podman networks here are IPv4-only, so the proxy has no IPv6 route. The networks are now created with `--ipv6=false` explicitly (`F4IPv4OnlyNetworks`), and the selftest checks a proxied IPv6 literal (`[2606:4700:4700::1111]:443`) fails in every mode. The suggested `2000::/3` deny acl was rejected: squid's `dst` acl matches if *any* address of a name matches, so it would refuse every dual-stack host, possibly including `api.anthropic.com`.

### 5. MEDIUM — Deferred-execution surface beyond git is only documented, and `.envrc` (direnv) is the sharp edge
**`agentbox/mounts.py:90-113` (only `.git/hooks`+`.git/config` made RO), threat model design.md:64**

Everything in the project root except `.git/hooks`/`.git/config` is agent-writable. The design mitigates git hooks specifically but leaves `.envrc`, `Makefile`, `package.json` scripts, `.pre-commit-config.yaml`, `.vscode/tasks.json`, `pyproject`/`setup.py`, etc. as writable. Most of these fall under the explicit non-goal ("code you later run executes as you"), which is defensible — **but `.envrc` does not require you to "run" anything**: with direnv installed, it executes as `vmuser` the instant you `cd` into the repo on the host, which is exactly the git-hook threat the design *does* mitigate.
- **Exploit:** Malicious repo or agent writes `.envrc`; you `cd ~/repos/x` on the host post-session → arbitrary code as vmuser.
- **Covered?** No.
- **Fix:** Be explicit in the design about which of these are mitigated vs. accepted (you asked for this). Consider adding `.envrc` to a read-only/masked overlay analogous to `.git/hooks`, since it is auto-executed, not "later run."

Per your request, here's the mitigate/document split for Q3:
- **Mitigated by code:** `.git/hooks`, `.git/config` (RO overlay, incl. submodules under `.git/modules`); `~/.config/{containers,systemd,autostart}`, `~/.local/bin`, shell rc files, `~/.ssh`, `~/.gnupg`, `~/.claude*`, `~/.omp` (never mounted — `paths.HOME_PROTECTED`); compose files RO in `lockdown`/`python`.
- **Only documented / accepted residual:** `.envrc`, `Makefile`, `package.json`/npm lifecycle scripts, `.pre-commit-config.yaml`, editor tasks, Python build scripts, and anything else inside the grant.

> **Response (builder, 30 Sep): REJECTED as stated for `.envrc`; the documentation part is done.** direnv does not execute a changed `.envrc`: any change blocks it until `direnv allow` is run again, so "executes the instant you cd" does not hold. direnv, mise and asdf are not installed on ubuntu-dev (checked 30 Sep). The mitigate/document split is now written into the design's filesystem policy (with a project `.venv`'s `.pth` files added to the documented list). Overlaying `.envrc` read-only would need an empty mount-point file created in every repo; not worth it for a tool that already requires consent.

### 6. LOW/MEDIUM — `.git` protection silently disappears when `.git` is a file (worktree / submodule checkout)
**`agentbox/mounts.py:94-98`**

If the project root's `.git` is a file (git worktree, or a submodule used directly as the project), `git_overlays` returns early with a note and **applies no RO overlay to hooks/config**. For a plain worktree the real gitdir isn't mounted so git can't reach planted hooks; but if the checkout's real gitdir happens to lie inside another grant, or the layout is a submodule-as-project, this is a hole. It's downgraded because reachability depends on layout, but the failure is silent (just a warn note).
- **Covered?** `test_git_file_is_noted` only checks a note is emitted, not that protection holds.
- **Fix:** For a `.git`-file root, resolve `gitdir:`/`commondir`, and if the real gitdir is within any grant, overlay its `hooks`/`config` RO; otherwise refuse or warn loudly.

> **Response (builder, 30 Sep): CONFIRMED, fixed, and widened.** Reproduced by `F6GitFileOverlays` (a `.git` file whose git dir is inside the grant got no overlay). While testing it, a wider gap turned up that the review did not list: a **nested repo anywhere in the grant** (vendored checkout, second clone, bare mirror) had writable hooks, because only the root's `.git` was handled (`F6NestedRepos`). Now every git directory inside a writable grant is found and its `hooks/`, `config`, `config.worktree` overlaid read-only: nested `.git` dirs, `.git`-file targets and their commondir, bare repos, submodule git dirs. A `.git` file pointing outside every grant is not mounted (noted at start).

### 7. LOW — `gc`/`teardown` will destroy a live session whose metadata is missing or corrupt
**`agentbox/session.py:449-452, 475-483, 487-493`**

`_alive` requires a readable `session.json` with a matching pid+start-time; if the file is missing/corrupt, `alive=False`. `gc()` (which runs automatically on the launcher's first use after boot, and via `ab gc`) then tears down every container/network carrying that session's label. There's a small window in `reserve_name`→`_write_meta` before the JSON exists, and any corruption/truncation (e.g., power loss mid-write; `_write_meta` is a plain non-atomic `open("w")`, unlike registry/token writes which use tmp+rename) makes a running session look dead.
- **Fix:** Write `session.json` atomically (tmp + `os.replace`, as elsewhere), and in `gc` treat "containers exist but meta unreadable" as a warning, not an automatic kill.

> **Response (builder, 30 Sep): CONFIRMED, fixed.** Reproduced by `F7GcKeepsRunningSessions`. `session.json` is now written atomically; gc leaves a session alone while its agent container runs (warning, `ab kill` to remove) but removes orphaned proxies and networks. While checking this, an interrupted `itest-oom` run was found to have left its proxy running: non-interactive sessions did not tear down on SIGTERM/SIGHUP. Fixed (both run modes now tear down on exit, Ctrl-C, SIGTERM, SIGHUP; unit test plus `test_sigterm_tears_the_session_down`).

### 8. LOW — Config-driven path traversal via `swap`, and the audit never validates mount **destinations**
**`agentbox/mounts.py:74-79` and `plan`; `agentbox/hardening.py:86-107` (`_audit_mount` checks `src` only)**

`swap` keys/values are joined onto `dirpath` with no basename check, so `swap = { "../../../etc/cron.d/x" = ".env.dev" }` would make `prepare()` attempt `os.open(<grant>/../../../etc/cron.d/x, O_CREAT|O_EXCL)` on the host and add a bind mount whose **dst** escapes the grant. The final `audit`/`_audit_mount` only validates that mount *sources* are inside grants; it never checks destinations, and `_no_commas` only rejects commas/newlines. `O_EXCL` (no `O_NOFOLLOW`, but EXCL blocks existing symlinks) and the fact that `swap` is Tim-authored config keep this low, but a value validator is cheap and the missing dst-audit is a latent hole for any future code that derives a dst from input.
- **Covered?** No.
- **Fix:** Require `swap` keys/values to be plain filenames (reject `/` and `..`); have `_audit_mount` also confirm the resolved dst stays within the container's intended tree.

> **Response (builder, 30 Sep): CONFIRMED, fixed.** Reproduced by `F8SwapAndMountDestinations`. `swap` keys and values must be plain file names; the argv audit now requires every mount destination to be a clean absolute path inside a grant or `/run/agentbox` (it checked sources only).

### 9. LOW — Proxy access log is retained and can contain secrets in plain-HTTP URLs
**`agentbox/session.py:403-416`, `agentbox/egress.py:120` (`%ru` logs full request URI)**

In `packages`/`open`, plain-HTTP GETs log the full URL including query string to `~/.local/share/agentbox/logs/<session>-proxy.log`, kept after teardown. HTTPS is CONNECT (host:port only), so this is limited, but an agent (or injected content) can push data — including its own token — into a logged `http://…?x=<token>` and it persists on disk. The design says the log "holds URLs, never headers," which is true but understates that URLs themselves carry data.
- **Fix:** Note the exposure; optionally strip query strings from logged URIs, or scrub known secrets before writing.

> **Response (builder, 30 Sep): partly CONFIRMED, fixed.** The query-string half does not hold: squid's default is `strip_query_terms on` (checked in the pinned image). The path half does. Reproduced by `F9ProxyLogHasNoPaths`; the log now records destinations only (`%>rd:%>rP`), with `strip_query_terms on` explicit, and the step 2 itest asserts no URL appears.
